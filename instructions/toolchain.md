## Blender and its MCP <a id="blender-mcp"></a>

Blender's own MCP (Blender Lab, `projects.blender.org/lab/blender_mcp`; the official one, never a community server (owner)) lets the agent drive the owner's open Blender. It has two halves, kept at matching versions:

- **The add-on** `mcp`, from the Blender Lab extension repository (id `lab_blender_org`, `https://lab.blender.org/`), enabled with auto-start: opening Blender starts its socket on `localhost:9876`. Blender's online access is off, so updating it takes the flag for that run: `blender --online-mode -c extension sync && blender --online-mode -c extension update`.
- **The server** `blender-mcp`, which Claude Code launches over stdio from `.mcp.json`, pinned to a commit of the repository. To upgrade it, move the pin to the commit matching the add-on's version.

**Blender is used sparingly** (owner): only for what can't be done without it; everything else stays in code (`docs/art-direction.md#procedural-first`). Its tools reach Blender only while the owner has it open; the session must be restarted to pick up a change to `.mcp.json`. It runs whatever Python it is sent with no guard, so it only opens this project's files. What is kept (a model, a rig, an export) is built by a script in the repository run with `blender --background`, so it can be rebuilt and reviewed; the MCP is for looking, trying and checking.

## What needs the GPU <a id="gpu"></a>

- **No GPU needed:** editing code and data, `dotnet build`, the unit tests, and the whole of `tools/check.sh` (every Godot step runs `--headless`), `tools/map.sh`. A laptop with the toolchain above (Godot .NET, the .NET SDK, ffmpeg) does all of it; the check is CPU-heavy (`instructions/testing.md#check-fast`; longer on a laptop).
- **GPU needed:** `tools/capture.sh` (photo spots, motion reels, frame times) and the owner's F12/F10 captures render in a real window with Vulkan. Visual work is judged from these captures, and frame times only mean something on the RTX 3060, so visual items (stage bricks, the pilgrim's look) are done on the desktop. Running them while a game uses the same GPU spoils the frame times.
- So code-only items can go on a laptop, or on the desktop while it is busy with a game; visual items need the desktop's GPU to itself while capturing.

## .NET environment <a id="dotnet-env"></a>

- The shell profile does **not** put .NET on `PATH`.
  - `tools/check.sh` sets `DOTNET_ROOT` and `PATH` itself.
  - The `godot` wrapper sets `DOTNET_ROOT`.
  - In ad-hoc commands, use `~/.dotnet/dotnet`, or first export `DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$PATH`.
- Without `DOTNET_ROOT`, Godot looks in `/usr/share/dotnet`, fails to load .NET, and a windowed run can appear to hang.
- Every shell command runs in a fresh shell, so environment variables don't carry over between commands.

## Known engine crashes <a id="engine-bugs"></a>

Godot 4.7.2's C# glue (GodotSharp) has two crash bugs that using it correctly (`instructions/godot-csharp.md#no-finalizer`) makes rare but can't remove:

- It hands native code unpinned pointers into managed objects, so a collection on another thread can move one mid-call: a rare SIGSEGV or "not registered" abort in a headless check, its stack in GodotSharp (a collection's or name's release, often on the finalizer thread).
- At editor shutdown, wrapper finalizers still pending run after the bindings are gone: the headless import can segfault on exit after a complete import (`!rc_owner` or `mono_gc_handle.cpp`).

A check that crashes this way is rerun; a crash whose stack reaches the project's code is the project's to fix. On an upgrade, rerun the full check several times to see whether they are gone, and drop this section when they are.

## Upgrading Godot <a id="upgrading-godot"></a>

`Godot.NET.Sdk` in `TheDeep.csproj` must stay at **exactly** the engine version. To upgrade:

1. Download the new **.NET** build from the official GitHub releases and verify it against `SHA512-SUMS.txt`.
2. Unzip it into `~/.local/opt/godot/`.
3. Point the wrapper at the new binary.
4. Update the SDK version in the `.csproj`.
5. Run `tools/check.sh`.
