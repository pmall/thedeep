# The Deep — agent guide

A gameplay-first 2.5D side-scrolling **metroidvania** (working title "The Deep"), built in Godot 4 .NET / C#.
The coding agent builds the whole game by editing text files; the owner only plays and gives feedback.

## Toolchain (confirmed)

| Tool | Version | Location |
|---|---|---|
| Godot Engine .NET | **4.7.2.stable.mono** (official, `ed1daf0bf`) | `~/.local/opt/godot/Godot_v4.7.2-stable_mono_linux_x86_64/` |
| `godot` command | wrapper script | `~/.local/bin/godot`: sets `DOTNET_ROOT=~/.dotnet` if unset, then execs the binary above |
| .NET SDK | **10.0.402** (plus .NET 8.0 runtime) | `~/.dotnet` (installed with `dotnet-install.sh`, no sudo) |
| Game target framework | `net8.0` (Godot 4.7 minimum; generated by Godot) | `TheDeep.csproj`, `Sdk="Godot.NET.Sdk/4.7.2"` |

- The shell profile does **not** put .NET on `PATH`. `tools/check.sh` sets `DOTNET_ROOT` and `PATH` itself, and the `godot` wrapper sets `DOTNET_ROOT`. In ad-hoc commands, use `~/.dotnet/dotnet` or export `DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$PATH` first. Without `DOTNET_ROOT`, Godot looks in `/usr/share/dotnet` and fails to load .NET.
- `Godot.NET.Sdk` must stay at **exactly** the engine version (4.7.2). Upgrading Godot means updating the `.csproj` SDK version too.

## Commands

| What | Command |
|---|---|
| **Check (run after every change and before every commit)** | `tools/check.sh` |
| Build only | `dotnet build TheDeep.sln` |
| Unit tests only | `dotnet test tests/TheDeep.Tests/TheDeep.Tests.csproj` |
| **Run the game (the owner's command)** | `godot --path .` |
| Regenerate `.uid` files / editor import | `godot --headless --editor --quit` |

`tools/check.sh` stops at the first failure:
1. `dotnet build` (nullable on, warnings are errors)
2. `godot --headless --import`, failing on any error line
3. Smoke test: (a) the main scene boots headless for 300 frames with no errors; (b) a scripted run (`-- --smoke`, see `scripts/debug/SmokeDriver.cs`) presses run/jump/dash through the real input actions and must print `SMOKE OK` (moved ≥ 10 m, full jump ≥ 2.9 m, every base state entered, never left Z = 0)
4. xUnit tests in `tests/TheDeep.Tests`

Logs go to `.godot/check/`. Never report work as done while the check fails.
`godot --path .` runs the last *built* assembly; it does not compile. The check builds, so after a passing check the owner's command is up to date.

### Seeing the game (visual verification)
Headless runs render nothing. To get real frames, use Movie Maker mode (it opens a window briefly):
`godot --path . --disable-vsync --fixed-fps 60 --quit-after 240 --write-movie /path/to/out/f.png -- --smoke`
`--disable-vsync` matters: with vsync on, the compositor throttles a background window to about 1 fps and the run looks hung. Write output into a fresh directory rather than deleting old frames.

## 1. What the game is

A side-scrolling metroidvania with a 2.5D look: the world is real 3D, the camera is fixed to the side, and play happens on a single 2D plane (Z = 0). Visual references: *Ori*, *Hollow Knight: Silksong*, *Castlevania: Belmont's Curse*.

Design priorities, in order:
1. **A finished, playable game.** No novel signature systems. Classic metroidvania structure done well.
2. **Ambience and art direction.**
3. **A small, defined set of abilities**, fixed before the map is designed, because the map is built around them.

**Setting.** A planet in the *Nirvanary* universe. Machines across many worlds seek "Nirvanary", a mythical machine paradise of infinite data and compute; on this planet they believe it lies at the planet's **core**. The player is a machine pilgrim descending through flooded, frozen and then volcanic layers toward it. **The game is a descent:** deeper means older, stranger, hotter. Narrative is out of scope for now: placeholder text only.

**Art direction** (for when real assets arrive):
- Dark and heavy, not pastel.
- The palette tracks depth: cold teal and rust near the surface, shifting to deep red and ember orange near the core.
- Environments: ruined pilgrim machinery, drowned halls of ancient servers, industrial cathedrals.
- Three depth layers: a blurred foreground, the play plane, and a hazy backdrop with parallax.
- Placeholder geometry (boxes, capsules, flat colors) until the movement feels good.

## 2. Moveset

**Base moveset (from the start), implemented:** run; jump with variable height (release early for a short hop), coyote time and jump buffer; **dash** on the ground and in the air (one air dash per airtime), with a short cooldown.

**Unlockable abilities (these gate the map), not implemented yet:**

| Ability | What it does | What it gates |
|---|---|---|
| **Mag-grip** | Walk on **metal** walls and ceilings. Rock cannot be gripped. | Vertical shafts and ceilings made of metal |
| **Harpoon** | Fire at an anchor point and zip to it | Gaps with anchor points |
| **Drill** | Break cracked rock | Cracked rock walls and floors |
| **Ballast** | Toggle between sinking and floating in water | Flooded layers |
| **Heat plating** | Passive: survive heat-vent zones | Late-game areas near the core |

Every ability is one simple state or rule. No systemic or emergent mechanics.

**Mag-grip implementation note.** Rotating the player around corners is the hard part. Use raycasts toward the surface plus `up_direction` aligned to the surface normal, and make corner transitions snap rather than flow at first; smooth them only once everything else works. Metal versus rock is a data property, the **physics layer** (`world_metal` vs `world_rock`, set by `Block.Surface`), never inferred from visuals.

## 3. Tech stack

- Godot 4 **.NET edition**, C#, Forward+ renderer, Jolt physics, physics interpolation on.
- `.csproj`/`.sln` were generated by Godot, then edited to add `<Nullable>enable</Nullable>`, `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`, `<RootNamespace>TheDeep</RootNamespace>` and `<Compile Remove="tests/**" />`.
  - `godot --headless --build-solutions --quit` does **not** create a missing csproj in 4.7.2. Godot only generates it when the editor saves a *new* C# script. If it ever has to be regenerated, run a throwaway `extends SceneTree` script with `godot --headless --editor --script x.gd` that `ResourceSaver.save()`s a new `CSharpScript` to a path that doesn't exist yet.
- 3D scene with a locked side camera: narrow-FOV (30°) perspective `Camera3D` at Z = +22 looking down −Z. Perspective rather than orthographic, so the depth layers get parallax.
- The player is a `CharacterBody3D` locked to Z = 0 (`axis_lock_linear_z` plus clamping in code). All gameplay physics stays on X/Y.
- Git from day one. Commit after each step that passes `tools/check.sh`.

## 4. How to work in this repo

- The owner never uses the Godot editor. Never ask them to do anything in it. `.tscn`, `.tres`, `.cs` and `project.godot` are text: edit them directly.
- **Never hand-invent `uid://` values.** Omit uids in new scenes and resources (`ext_resource` by `path` only), or let `godot --headless --editor --quit` generate them. Godot writes `*.cs.uid` files next to scripts: commit them.
- Never edit `.godot/` or `*.import` files (generated). Do commit `*.import` files.
- Keep scenes small and composed, one responsibility each.
- **Godot C# rules the compiler won't always flag:**
  - Every Godot script class is `public partial class`, and its name matches its file name exactly (`Player.cs` → `class Player`).
  - Custom resources are `[GlobalClass] public partial class X : Resource` with `[Export]` properties.
  - After adding or renaming a class, rebuild before referencing it from a scene.
  - Put `///` doc comments *before* all attributes (e.g. before `[ExportGroup]`), not between them.
- **No code the compiler can't see:** no string node paths across scenes (`GetNode("A/B")`). Use typed `[Export] public NodeType X { get; set; } = null!;` references (in `.tscn`: list them in the node's `node_paths=PackedStringArray(...)` and assign `X = NodePath("../Y")`), or `GetNode<T>("%UniqueName")` within one scene. Connect signals with C# events (`button.Pressed += OnPressed;`), not `Connect("name", ...)`. Use `SignalName.X` / `PropertyName.X`, never string literals.
- `.tscn` `Transform3D(...)` values are the basis **row-major** (`x.x, y.x, z.x, x.y, …`) followed by the origin.
- Bulky scene text (the test room layout) may be generated with a small script. If you do, keep the generated `.tscn` readable, because the `.tscn` is the source of truth.

**Pure logic** (no Godot types, compiled straight into the xUnit project via `<Compile Include>`): `util/Motion.cs`, `util/Countdown.cs`, `tuning/JumpMath.cs`, `camera/CameraMath.cs`, `abilities/Ability.cs`, `abilities/AbilitySet.cs`. Keep these Godot-free. When adding testable logic, put it in a Godot-free file and add it to `tests/TheDeep.Tests/TheDeep.Tests.csproj`.

## 6. Conventions

- Standard C# naming: PascalCase types, methods and properties; `_camelCase` private fields. One class per file. Namespace `TheDeep` (states: `TheDeep.States`).
- A small explicit state machine for the player, one state per class: each tick the active state sets velocity and returns the next state (or null); `Player` then calls `MoveAndSlide`. No giant `_PhysicsProcess`.
- **All movement tuning** (speeds, accelerations, jump height/time, cut factor, gravity multipliers, coyote time, jump/dash buffers, dash distance/duration/cooldown) lives in `resources/player_tuning.tres`, never hard-coded. Camera and visual feel numbers are `[Export]`s on their scenes.
- **Physics layers**, defined once in `project.godot`, mirrored in `PhysicsLayers.cs`: 1 `world_rock`, 2 `world_metal`, 3 `player`, 4 `enemy`, 5 `hazard`, 6 `water`, 7 `trigger`. Code sets layers from these constants (`Player` and `Block` do so in `_Ready`).
- **Input actions**, defined in `project.godot`, mirrored in `InputActions.cs` (no string literals elsewhere): `move_left`, `move_right`, `move_up`, `move_down`, `jump`, `dash`, `attack`, `interact`, plus `debug_respawn` and `debug_toggle_{mag_grip,harpoon,drill,ballast,heat_plating}`.
  - Keyboard: A/D or arrows move, W/S or up/down, Space or Z jump, Shift or C dash, J or X attack, E interact, R respawn, F1–F5 ability toggles.
  - Gamepad: left stick / d-pad move, A jump, RB or RT dash, X attack, Y interact, Back respawn.
- Abilities are unlocked through `AbilitySet` flags (`Player.Abilities`); F1–F5 toggle them in debug builds.
