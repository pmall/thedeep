# Architecture

## Tech stack

- Godot 4 **.NET edition**, C#. Forward+ renderer, Jolt physics, physics interpolation on.
- 3D world with a locked side camera: a narrow-FOV (30°) perspective `Camera3D` at Z = +22 looking down −Z.
- The player is a `CharacterBody3D` locked to Z = 0 (`axis_lock_linear_z` plus clamping in code). All gameplay physics stays on X/Y.
- Versions and install paths: [toolchain.md](toolchain.md). Working with Godot files as text: [godot-csharp.md](godot-csharp.md).

## Layers

The rules are in [principles.md](principles.md): **core** (pure C#, no Godot: rules, state, the map and solver, brains, geometry), **adapters** (thin Godot nodes that connect the core to the engine), **content** (scenes, resources, data: rooms, species, biomes, lines, worlds). Dependencies point one way: content → adapters → core.

Where the code stands (2026-11-01, roadmap item P1 done):
- **The core** is its own project, `core/TheDeep.Core.csproj` (plain .NET, no Godot reference, so a Godot type there does not compile), referenced by the game (`TheDeep.csproj`, which keeps `core/**` out of its own sources) and by the tests. Its files keep the folder names of the adapters they serve (`core/map/`, `core/player/`, ...) and the namespace `TheDeep`.
- **Adapters** live in `scripts/`. The biggest ones hand their rules to the core: `Player` to `PilgrimControl` and `MoveRules`, `Session` to `Pilgrimage`, `Machine` to `MachineVitals`, `CrawlMotion` and `MachineGait`, `RoomValidator` to `WorldCheck`. Vectors cross the seam only through `scripts/engine/Numerics.cs` (`ToCore`, `ToGodot`, `Flat`, `OnPlane`); a tuning resource gives the core its numbers as plain records (`PlayerTuning.Control`, `.Move`, `.Harpoon`, `.Grip`, `.Water`).
- **A world is content** (`worlds/<name>/`): a `WorldDefinition` (`world.tres`) names its rooms folder, its network file, its start room, its layers and their biomes, its line book and its save. `World.Definition` (set in `Main.tscn`: the prototype) is the world played; `--world <name>` plays another. No code knows the prototype's rooms, network or layers; checks may name its rooms.

## Design patterns

- **Player state machine:** one class per state in `scripts/player/states/`. Each physics tick the active state sets velocity and returns the next state (or null); `Player` then calls `MoveAndSlide` and keeps the body on Z = 0. The states ask `Player` for the shared timers and movement helpers, which it answers from the core (`PilgrimControl`: the presses kept, coyote time, cooldowns, air dashes, stun; `MoveRules`: running, gravity, a blow's throw). No giant `_PhysicsProcess`.
- **Composition:** scenes are small, with one responsibility each. `Main.tscn` wires the room, player, camera, HUD and cheats together through typed `[Export]` node references.
- **Materials:** a material is a `.tres` (`ShaderMaterial`) referenced by blocks and scenes, never a shader assigned in code, so an authored material can replace it. Shaders read colors from the biome palette and the piece's **surface frame** from its mesh (`lib/surface.gdshaderinc`): UV is the position on a rectangular patch (a box face, one side of a swept profile) in meters, UV2 the patch size (negative along an axis that wraps, like a pipe's girth), TANGENT/BINORMAL the patch directions, COLOR.r the height above the piece's bottom (/ 8 m, 8-bit) and COLOR.g a per-part variation. Panels, seams and edge wear follow any kit piece that way, curved or not, with no texture UVs and no triplanar blending. A block's look can be overridden (`Block.Material`: wet stone, rust…) without touching its `Surface`, which alone decides the physics layer. Pieces behind the play plane use the `*_mid` materials (`shade` < 1), so the play plane stays the brightest layer and only grippable metal reads as bright metal.
- **Environment kit:** each piece is a `[GlobalClass]` mesh resource (`ColumnMesh`, `ArchMesh`, `PipeMesh`…) deriving from `KitMesh : PrimitiveMesh`, used by a plain `MeshInstance3D`. Its geometry is pure C# (`KitShapes`, `MeshBuilder`), unit tested. Rooms place pieces as sub-resources (pieces sharing one resource share one generated mesh). Swapping in authored art means replacing the mesh resource; an authored mesh keeps the procedural materials only if it carries the same surface frame. Kit pieces are visual only: gameplay collision is `Block` boxes (`CollisionOnly` when a kit piece shows the block, like the grate platform).
- **Biomes:** a room references a `BiomeProfile`. `Room.ApplyBiome` pushes the palette into global shader uniforms (`[shader_globals]` in `project.godot`, names in `ShaderGlobals`) and sets the room's environment, key light and lamps. Materials read the palette from those globals, so they follow the biome without per-room copies, and an authored material can replace a procedural one and still use them. Machines take their colors from the same palette (`machine.gdshader`). The biome's `Frost` lays rime on rock, metal (a smaller share, so grippable metal keeps its gloss) and ice through `lib/frost.gdshaderinc`, and on machines while they are dormant (it falls away as they rouse); 0 in the flooded layer. The biome also sets the volumetric fog, the color of the room's light shafts (`Room.Shafts`) and glyph lights (`Room.GlyphLights`), the far haze, water colors and caustics, and the finishing pass (vignette, grain) through `post_*` globals.
- **Level toolkit** (M6): a room instances `scenes/stage/RoomStage.tscn` as `Stage`; `Room._Ready` calls `Stage.Build(room)`, which sizes the shared stack from the camera bounds (environment `resources/stage/room_environment.tres`, key light, `ClearFront`, skylines, frame above and below, dust); then, on every biome change (`Stage.Restyle`), the depth layer's own skylines, its underglow, and its architecture in the haze (`BackdropArchitecture`: rows of kit pieces at three depths in the biome's `BackdropStyle`, nave, stacks, foundry or machinery, laid out by the pure `BackdropLayout` and drawn as one multimesh per piece and row). A room overrides only the stage's choices (pillar density: how many architecture rows, 0 for none; frame on/off, dust density, seed) and adds what is its own: shafts, lamps, water, extra particles, framing pieces like a pipe. Repeated dressing comes from generators in `scripts/rooms/dressing/` (`Colonnade`, `RackRow`) placing swappable mesh resources from a seed; their layouts are pure (`DressingLayout`) and tested. Generated nodes are not owned by the room, so `RoomValidator` checks only the generator node's own origin.
- **Atmosphere in a room** (M3): light shafts are shadowed `SpotLight3D`s listed in `Room.Shafts`; a negative-density `FogVolume` (`fog_clear.tres`) keeps volumetric fog off the space in front of the play plane; ambient particles are instances of `scenes/fx/*.tscn` with `Extents` and `Density` set; water is a `WaterBody` (one per room for now: the water globals hold one level and area). Visual only: nothing here touches gameplay or collision.
- **Rooms:** each room is its own scene in its world's rooms folder (`worlds/prototype/rooms/`) with a `Room` root: spawn point, camera bounds, biome, photo spots, and `RoomExit` markers. `World` (in `Main`) loads one; nodes that need the room (camera, cheats, capture) reference `World` and read `World.Room`. An exit's `Requires` is for leaving through it; the way back is the target exit's own, and a two-way exit's target must lead back (`OneWay` otherwise). `RoomValidator` (in `tools/check.sh`) checks every room: block edges on the 0.5 m grid and axis-aligned, kit piece origins on the 0.25 m grid, spawn and exits inside the bounds, exit requirements parse, targets exist and lead back, at least one photo spot. **Travel** (M6): an open exit (with a `TargetRoom`) makes a trigger area on the `trigger` layer; walking into it raises `Crossed`, and `RoomTravel` holds the player under a short fade (`ScreenFade`), loads the target room (rooms always sit at the world origin), places the player at the arrival exit keeping its momentum (`ExitMath`: the offset along a wide hatch is kept, a doorway keeps the height), disarms the arrival exit until the player leaves it, and fades back in. The camera snaps on `Player.Arrived`; each room's camera bounds are its own. A doorway (a tall exit) is only left by moving or pressing out of the room, toward the nearer side of its bounds (`ExitMath.Leaves`): dropping into one from a flue above, or standing in one, never travels; a hatch is crossed whatever the way. `World.Map` places each visited room from the exits crossed (no hand list), keeps each visited room's ways out (`MapWay`, from its exit markers) and the ways taken (left or arrived through), all saved: the map screen draws the rooms and the ways not yet taken. `TravelValidator` crosses every open exit in `tools/check.sh`.

- **Machines** (M5): one `Machine` node type for every species; a room places `Machine` nodes (in `Machines`) pointing at a `MachineSpecies` `.tres`. The species holds everything else: its body (a `PartAssembly` in `resources/parts/`, the same part system as the pilgrim), its locomotion (`Walk` on the ground, `Hover` in the plane, `Crawl` over the faces of the metal block it starts on, found from the physics layer), its stats and palette, its behavior and its animation. The behavior is a `MachineBehavior` resource exporting the knobs of one **brain**: a pure class (`machines/brains/`) that turns a `Perception` into an `Intent` each tick, built from the vocabulary (`Senses`, `Steering`, `PrayerCycle`, `StrikeAction`) and unit tested without the engine. The intent's channels (`Pray`, `Strike`, `Alert`, `Rouse`, `Work`) and the machine's speed drive its animation as data: `JointDriver`s pose, wave, spin or aim joints, `MachineLeg`s step by IK with planted feet. `MachineDirector` (in `Main`) collects the room's machines when it loads, builds their perception (the player's chest and line of sight on the world layers, impacts from the player's landings and dashes, neighbors and what they broadcast) and steps them in scene order, so look-dev and checks are deterministic. Adding a species is one `.tres` (and its body); a brain only for a truly new behavior. A strike's wind-up always comes before the blow, and only hostile species' eyes turn the hazard color. `SpeciesValidator` (in `tools/check.sh`) checks every species' data and runs each one alone in the arena, without and with the player.
- **Combat and session** (M6): `PlayerAttack` (a child of the player) raises `Striking(area, swing)` while a swing's hit window is open; `MachineDirector` hits each machine whose `BodyRect` the area reaches once per swing (`Machine.TakeHit`: flash through the `hurt` instance uniform of machine.gdshader, stagger, knockback, breaking) and turns machine blows into `Player.TakeHit`. `Session` (in Main) handles shrines, relics, death and the return to the last shrine, and the save (`SaveData` ↔ `user://save.json`); `Main` resumes from the save on a normal launch. Text shown (the "Rest" prompt, ability banners) comes from the line book.
- **Lifts** (M8): a `Lift` (`scenes/props/Lift.tscn`) is a prop, not a `Block`: its cage is an `AnimatableBody3D` on the rock layer that carries the pilgrim (the character body rides a moving floor), driven each physics tick by the pure `LiftMotion` (so the travel is unit tested). `Session` hands it the player when a room loads (riding is standing upright on its floor) and shakes the camera when its brake lets go; it holds still while the player is frozen (travelling under the veil). The geometry check sees it as a `LiftPath` (the platform at its lower stop, its rise): `ReachPlanner` stands on it there and rides it up, touching every trigger the body passes through, so an exit at the top of a shaft can need nothing. A lift that carries the pilgrim into another room ends in a hatch exit at its upper stop; the far side is an arrival-only exit on solid floor (the Undercroft's grate), since nothing goes back down that way.
- **Water** (M8, Ballast): a `WaterBody` with `Swim` makes an area on the `water` layer over its region of the play plane (Size.X wide, from its surface down Depth); the player finds the surface over its feet each tick (`Player.WaterSurface`, a point query) and `SwimState` moves it with the pure `WaterMotion`. Visually the water's front is a section quad (the cut, seen from the side) in front of the blocks, and its haze stays behind the play plane. Only one water body per room drives the water globals (caustics, the haze's level); a second one (the Descent's flooded gate beside its scenery water) sets `Globals` off. The geometry check reads each swimmable body's `PlayRegion`: every planner floats in it with the player's own motion (float lines are ledges to jump from; floors deeper than a jump out are not), and a Ballast planner reaches every point of the water connected to where it went in (`ReachPlanner`, a flood fill of feet positions). Water from one room to the next meets at hatches and doorways; each room's water has its own surface.
- **Heat** (M8, Heat plating): a `HeatZone` is a prop, not a `Block`: `Session` hands it the player when a room loads, and it burns (or, during the grace period, repels) a player without Heat plating whose body overlaps its region. The geometry check reads each zone's `Region` as space a planner without Heat plating never enters (a trajectory touching one ends; ledges and water cells are cut by it); entries through a way only Heat plating opens are planned with it.
- **Cracked rock** (M8, the Drill): a `Block` with `Cracked` (rock layer, cracked look). The player tests its own motion ahead each tick while in a state that bores (`PlayerState.Bores`: the dash, the dive) and breaks the cracked block it would hit (`Block.Break`: off the layers at once so the same tick's move goes through, a `Shatter` for the look). `Session` remembers each broken block by room and name and settles it on later visits. The geometry check has a third planner with cracked rock removed: an exit that needs the Drill must be reached by it from some way in.
- **Bosses and law breaks** (M8): a boss is an ordinary `Machine` (its species and brain as data) inside a `BossSeal` arena whose `Portcullis` gates fall while it stands; a law break is a `LawBreak` at a lip. Neither is a `Block`, so the map and the geometry check see the ways as open (law breaks are story beats outside the ability graph, docs/theme.md; the draft models them as `milestone`s). `Session` hands them the player when a room loads and remembers each one done, with relics, in `SaveData.Collected` as `Room/NodeName`; on later visits it calls their `Settle`. Falling below a room's camera bounds (a drop into a room not built yet) returns the pilgrim to its last shrine.
- **Text** is data: the world's line book (`WorldDefinition.Lines`; the prototype's `worlds/prototype/lines.tres`, a `LineBook`) holds every line with a stable id, a speaker and delivery notes; the `World` makes it the book every line is read from (`LineBook.Shared`) as it enters the tree. Species point at their creed by id.
- **Worlds** (P1): a `WorldDefinition` is the whole of a world's content: `RoomsFolder` (a room's name is its scene's file name there), `Network` (a markdown file whose `map` blocks `MapDraft` parses: rooms and their layers, ways, relics, bosses, milestones, start, goal, `target` statements), `StartRoom`, `Layers` (`WorldLayer`: the name the network gives, its biome; F6 cycles them), `Lines`, `SaveName` (`user://<name>.json`). The room check reads the world's rooms and network and holds them to each other (and the network's layers to the world's).
- **Required exports**: an export a scene must set is declared non-null (`= null!`, injected by the engine); the room check fails on any left empty (`RequiredExports`, by reflection on the nullability of `[Export]` properties): in every room's nodes, the bricks they place and the resources their exports reach, and in the main scene as authored and its world. An export a scene may leave empty is `T?`, and the code says what happens without it.

## The core

`core/TheDeep.Core.csproj` holds every Godot-free file: the rules and the state (movement and water math, the pilgrim's controls and speed rules, abilities, combat, health, the save, the run's progress, the map graph, solver, layout, network and world check, the reach planner, machine brains, the behavior vocabulary, a machine's condition, crawl and gait, mesh geometry, layouts, humanoid poses), and the capture tooling's pure parts (file names, reports, the video clock, ffmpeg's arguments and the encoder process). The tests (`tests/TheDeep.Tests`, xUnit) reference it; `VideoEncoderTests` run the real ffmpeg.

Every new game rule goes here, with its tests, not in a node ([principles.md](principles.md)). A file here may use .NET and `System.Numerics` only: the project has no Godot reference, so anything else does not compile. Godot `[Export]` properties may use the core's enums (`Ability`, `Locomotion`, `SurfaceKind`, ...): they are plain C# enums.

## Rules that keep the long-term objectives cheap

- No code knows one world: room names, species ids, layers and content paths come from content ([long-term.md](long-term.md), objective 3).
- Rooms are separate scenes. Connections are **marker nodes inside the room scene** that carry an ability requirement expression and a one-way flag. Never keep a hand-maintained list of connections.
- Machines are data (`MachineSpecies` `.tres`) plus one behavior class. Never one scene per machine.
- The player and the machines are built from the same modular part system.
- All movement limits stay in `player_tuning.tres`.

## Code conventions

- **Per-frame code allocates nothing** (`_Process`, `_PhysicsProcess` and what they call). A garbage collection is a dropped frame, and engine objects (arrays and dictionaries from the engine, query parameters, node wrappers) are finalizable, so they survive into gen1 and make every collection slow. Keep buffers and reuse them (`KitMesh.Buffers`, `MeshBuilder.Clear`, `SweepPath.FromPoints(…, frames)`), ask the room for nodes through `Room.All<T>()` (kept, never walk the tree per tick), avoid LINQ and `GetChildren()` per tick. `tools/capture.sh` reports the collections in each run (`gc` in `perf*.json`); a scripted run should see a handful, not one every few frames.
- Standard C# naming: PascalCase types, methods and properties; `_camelCase` private fields. One class per file, with the file named after the class.
- Namespace `TheDeep` (player states: `TheDeep.States`).
- Nullable reference types on, warnings are errors. Exported references a scene must set are declared `= null!;`, and that is the only place `!` is allowed; typing rules in [principles.md](principles.md) ("Types tell the truth").
- `unsafe` is allowed in the game assembly only for `FrameGrabber`, which copies frames out of Godot's native buffers through `Godot.NativeInterop` to avoid multi-megabyte allocations every frame, and `NativeMeshArrays`, which writes a chain's mesh arrays straight into the engine array (through the managed indexer each packed array registers a finalizable disposer: seven per chain per frame). Don't spread it.
